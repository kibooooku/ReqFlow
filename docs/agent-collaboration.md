## 协作机制

1. 主控先写PRD、架构和API契约，各代理按文件边界独立工作。
2. 研究与前端并行，报告模板同时检查；业务实现时主控编写HTTP适配及测试。
3. 接口变化通过代理消息同步，统一以docs/api-contract.md为准。例：验证项增加revision，PATCH须传expected_revision。
4. 保存初版源码快照后，针对真实问题添加回归测试；初版失败和最终修复结果均留存。
5. 审查由未编写被审模块的代理完成；主控复核业务层和集成。报告代理只引用实际运行证据。

## grill实际使用

先从已接受方案及作业截图解决已知范围，再问一个影响权限的分支：“提交人能否批准自己的需求或变更？”建议不同成员审批，用户选择“不同成员审批（推荐）”。此决策落实为评审/变更后端禁止自审以及对应自动化负向测试。用户还要求在报告中说明两个技能的作用，已纳入两份报告。

## architect实际使用

在明确需求后比较FastAPI/原生HTTP/Java、原生前端/框架、SQLite/PostgreSQL/JSON、会话Cookie/浏览器令牌等方案。产出文件树、模块依赖、实体字段关系、阶段依赖及验收条件。用户“开始完成吧”已授权设计与实现；执行由当前多智能体工具编排，没有创建Archon campaign。
